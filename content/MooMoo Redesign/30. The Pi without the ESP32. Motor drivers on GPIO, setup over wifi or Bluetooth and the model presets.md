# Goals
- Drive the six dots and read the six buttons from the Raspberry Pi alone, without the ESP32 of the first workbook
- Let a parent or another maker put the Pi on a home network from a phone, through a temporary Moo network or over Bluetooth
- Run the speech and language models from the Pi itself, with the key kept on the device
- Keep the motor drivers switched off whenever the code is not in control of them

# Description
In the first workbook the device needed two computers. The ESP32 drove the motors through TB6612FNG boards and read the buttons through an MCP23017 expander, while the Raspberry Pi Zero 2 W handled the microphone, the speaker and the calls to Whisper and ChatGPT, and sent each letter to the ESP32 over UART (see [[15. Raspberry Pi Zero 2 W and ESP32 UART connection]] and [[17. Interactive Connection to Raspberry PI Zero 2W and ESP32. Chat GPT response and storytelling testing and user flow.]]). The boards did not fit in the casing and moved to a second compartment ([[18. Additional Compartment for Electronics.]]).

The redesign keeps only the Pi. In the maker's account the TB6612FNG boards are wired straight to the Pi, and the Pi joins a network by itself, through a separate wifi network or over Bluetooth, and runs the model APIs on its own. The code bears this out. `braille_gpio.py` describes a driver with everything wired to the Pi and no I2C expander, and `braille.py` names it the single backend. The ESP32, the expander, the UART link and the aluminium foil stop of [[10. Motor block aluminum sensor and AI-Thinker Board]] are gone, and the electronics sit inside the bottom shell (step 28).

The six dots are display and input at once. Raising a letter drives the motors of its dots forward. Pressing the button under a raised dot drives that motor backward and lowers the dot, so a child who has felt a letter clears it with the same fingers.

The maker plans two presets on the Pi, a local AI model and the cloud ChatGPT model, as a high quality and a low quality preset. On 3 November 2026 the local model was not yet implemented, and the code, last saved on 22 July 2026, calls only the cloud models listed below. The redesign chats compared local and cloud speech and language models on 21 December 2025, and on 1 May 2026 chose Vosk speech recognition on the Pi with a cloud language model and cloud speech.

# How it works
## One computer and three driver boards
| Line | From the Pi to | Lines |
|---|---|---|
| Direction, AIN1 and AIN2 | Each of the six H bridge channels on three TB6612FNG boards | 12 |
| Standby | All three boards, tied together, on GPIO 26, pulled down at boot | 1 |
| PWM | Tied to 3.3 V on the boards, so the motors always run at full speed | 0 |
| Buttons | One push button under each dot, read with the internal pull up | 6 |

| Move | AIN1 | AIN2 |
|---|---|---|
| Raise the dot | High | Low |
| Lower the dot | Low | High |
| Stop and coast | Low | Low |

The pin numbers are not fixed in the code. The driver reads them from the configuration file, which the calibration of step 31 writes.

## Setting it up from a phone
The Pi serves a web app to the phone, and the same app is published as a hosted dashboard. The connect screen offers two ways in.
- **Bluetooth, stay on your wifi.** The phone finds the Pi over Bluetooth Low Energy and stays on its own network. It needs Chrome or Edge, and accepts an optional six digit code if one is printed on the device.
- **Temporary Moo wifi.** When the Pi knows no network, Comitup makes it open its own network, named moo followed by a number. The phone joins it, and the app calls this the original setup method.

Through either way the phone lists the networks the Pi can see, sends the home network and its password, and finds the Pi again on the home network. The first setup then asks for the OpenAI key, the preferences and an audio test. The preferences are the storytelling voice, an age range of 0 to 3, 3 to 5 or 5 to 8, the volume and the language. The dashboard leads on to calibration, the audio test, letter practice and the story.

## The models
| Task | Model in the kept code | Where it runs |
|---|---|---|
| The child's speech to text | `whisper-1` | Cloud. A comment in `audio.py` notes that Whisper on the Pi would run out of its 512 MB |
| Story, quiz and the spelling word | `gpt-4o-mini` | Cloud |
| Safety check of each story before it is told | `omni-moderation-latest` | Cloud |
| The voice | `tts-1` | Cloud |

The key is kept in `/etc/moo/config.json` on the Pi, readable only by its owner, and it is masked whenever the configuration is read back to the phone. The device counts as set up once it has both a key and a home network.

The storyteller runs as a session with a greeting, listening, thinking, telling, a quiz and a spelling game. In the spelling game the letters of one word from the story come up one at a time, and the child feels each raised dot and presses it down before the next letter comes.

```ts
const STORAGE_KEY = "moo_transport";

export function getTransportKind(): TransportKind {
  if (typeof window === "undefined") return "wifi";
  return window.localStorage.getItem(STORAGE_KEY) === "bluetooth" ? "bluetooth" : "wifi";
}
```

# Critical Reflection
## One computer instead of two
**Pros**
- One board, one program and one supply. The UART link, the expander and the second compartment of the first workbook are gone
- Every pin assignment lives in one file and is set from the phone (step 31), so the motors and buttons can be wired in any order
- The drivers stay off until the code has set every direction line low

**Cons**
- Twelve direction lines, six buttons and the standby line take 19 GPIO pins of the Pi
- Motors and computer share the 5 V rail of the Pi (step 29)
- The cloud models need a home network, an OpenAI account, a key and money for every session. The local preset the maker plans would answer part of this, and it is not implemented yet

## Setting up from a phone
**Pros**
- No terminal. A parent or a maker sets the device up from a phone browser
- The temporary network works with any phone, and Bluetooth keeps the phone on its own wifi
- The key stays on the device and is never shown again in full

**Cons**
- Bluetooth setup needs Chrome or Edge, so a phone without them falls back to the temporary network
- The setup is a set of visual web pages. The files do not show a test with a screen reader, which matters for blind parents and makers

## Two things to check in the code
- The opening comment of `braille.py` of 15 May still says that standby is tied to 3.3 V on the boards, while `braille_gpio.py` of 19 May puts it on GPIO 26. The device runs the second
- `_is_safe` in `assistant/story.py` treats a failed moderation call as safe, so a story is told unchecked whenever the moderation service cannot be reached
