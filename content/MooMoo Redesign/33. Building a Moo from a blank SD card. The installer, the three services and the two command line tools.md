# Goals
- Turn a blank SD card into a working Moo with one script, so that the device can be rebuilt by someone other than its maker
- Run the setup app, the storyteller and the Bluetooth bridge as services that start by themselves and come back after a crash
- Give the setup app the few system commands it needs, and nothing more
- Make one finished card that can be copied for further devices without carrying the first device's network, key or identity

# Description
Steps 29 to 31 describe what the Pi does once it runs. This step describes how it gets there. Everything is in the `pi` folder of the code. `install.sh` prepares a fresh Raspberry Pi OS, three systemd units keep the programs running, a sudoers file lets the setup app run eight commands as root, and two small command line tools set the key and report the state of the device. `prepare_image.sh` cleans a finished card so it can be copied. The installer was first written on 9 May 2026 and last changed on 22 July 2026, when the Bluetooth bridge was added.

The installer says of itself that it can be run again safely. It deletes and copies the code folder each time, so running it after every larger change is also how the code on the Pi is replaced as a whole.

# How it works
## From a blank card to a Moo
1. Write Raspberry Pi OS Lite, 64 bit, Bookworm or Trixie, to the card. Create the user the code expects, `philipn1` (see Critical Reflection), and give the Pi a network for the first start
2. On the Pi, install Comitup by hand with `sudo apt install comitup`. The installer needs it and does not install it
3. On the Mac, run `build.sh` to build the setup app into `pi/setup_service/static`, then copy the `pi` folder to the Pi
4. On the Pi, run `./install.sh` from inside that folder, then `sudo reboot`
5. Optionally write a six digit code to `/etc/moo/ble-pin` for the Bluetooth setup (step 30)
6. Set the device up from a phone over the temporary network or Bluetooth (step 30), or over SSH with `moo-setup`
7. Calibrate the dots (step 31)

## What the installer does
| Part | What it does |
|---|---|
| Packages | Python tools, PortAudio, OpenBLAS, the GPIO library, ffmpeg and mpg123 for sound, ALSA tools, Avahi for the `.local` name, BlueZ, rfkill, iw and I2C tools |
| Name | Sets the host name to `moo`, so the device is found as `moo.local` |
| User | Adds the user to the dialout, audio, gpio and i2c groups |
| Interfaces | Turns on I2C and the serial port, keeps the onboard Bluetooth, and sets the single USB data port to host mode for the sound card (step 32) |
| Folders | `/etc/moo` for the configuration, readable only by the user, and `/opt/moo` for the code and its Python environment |
| Code | Deletes `/opt/moo/pi`, copies the folder it was started from into it, and installs the pinned libraries into `/opt/moo/venv` |
| Tools | Puts `moo-setup` and `moo-status` into `/usr/local/bin` |
| Services | Installs and enables the three units below, the sudoers file and the Comitup configuration |

The part of `pi/install.sh` that names the device, makes the folders and copies the code. Every line prints what it is about to do, so a failed install shows where it stopped.

```bash
echo "==> Hostname → moo (mDNS will publish moo.local)"
sudo hostnamectl set-hostname moo

echo "==> Creating /etc/moo"
sudo install -d -m 0700 -o "$MOO_USER" -g "$MOO_USER" /etc/moo

echo "==> Copying Pi sources to $PI_SRC_DIR"
sudo rm -rf "$PI_SRC_DIR"
sudo install -d -o "$MOO_USER" -g "$MOO_USER" "$PI_SRC_DIR"
sudo cp -r "$THIS_DIR"/* "$PI_SRC_DIR"/

echo "==> Building venv at $VENV"
sudo -u "$MOO_USER" python3 -m venv "$VENV"
sudo -u "$MOO_USER" "$VENV/bin/pip" install -r "$PI_SRC_DIR/requirements.txt"
```

## The three services
| Service | Runs | As | When it stops |
|---|---|---|---|
| `moo-setup` | The setup app and its API, on port 8000 of every network the Pi is on | The user | Starts again after 5 s, always |
| `moo-assistant` | The storyteller that listens to the child, `python -m assistant`. Only starts when a configuration file exists, and only together with `moo-setup` | The user | Starts again after 10 s if it failed |
| `moo-bluetooth` | The Bluetooth bridge of step 30. Unblocks the radio and makes it visible and pairable first | Root, with its home folders hidden and no way to gain more rights | Starts again after 5 s, always |

The setup app can start, stop and restart the storyteller, scan for networks, hand a network to Comitup, make Comitup forget it, and read the last lines of the two logs. The sudoers file allows exactly these eight commands without a password and nothing else.

## The two command line tools
`moo-setup` asks for the OpenAI key without showing it, checks that it starts with `sk-` and that OpenAI accepts it by listing the models, allows three tries, saves it to the configuration file and restarts the storyteller. `moo-setup --reset` deletes the configuration after asking. `moo-status` prints the configuration with the key masked, the voice, age range and volume, whether the storyteller runs, the sound devices it can see and the last ten lines of the storyteller's log.

## Making copies
`prepare_image.sh` is run as root on a finished device just before its card is copied. It stops the services and deletes everything that belongs to that one device. That is the configuration with the key, the saved wifi, Comitup's state, the SSH host keys, the machine id, the logs and the shell histories. A small service it installs makes new SSH host keys on the first start of each copy. Every copy therefore starts as a new device with the temporary network open.

# Checked on the device, 20 November 2026
The three services are installed and enabled on the Pi. The setup app listens on port 8000 and the Bluetooth bridge advertises itself as `Moo-7331`. The storyteller service does not run. Its log shows the same error at every start, `No module named assistant.__main__; 'assistant' is a package and cannot be directly executed`, followed by a new attempt ten seconds later. The unit starts the package `assistant`, but the package has no `__main__.py`. Its program is `assistant/main.py`. The log goes back to 22 July 2026 and records 73 starts, all of them failed. Stories started from the phone are not affected, because the story and letter screens run inside the setup app.

# Critical Reflection
## One script for the whole device
**Pros**
- A blank card becomes a Moo with one script and a reboot, and the steps are short enough to print
- The services start by themselves and come back after a crash, so a child never sees a terminal
- The setup app gets eight root commands by name instead of full root rights
- Copies made with `prepare_image.sh` carry no key, no network and no identity of the first device
- The library versions are pinned, so a device built later gets the same libraries

**Cons**
- The user name `philipn1` is written into the three services, the sudoers file and the owner of the configuration. The installer lets the name be changed with `MOO_USER`, but the other four files do not follow it, so a builder has to use the same name or edit them by hand
- Comitup has to be installed by hand before the installer runs
- The installer still turns on I2C with the comment MCP23017 and MPR121, and the serial port with the comment ESP32 fallback. Both belong to the first workbook. `moo-status` still says it checks the ESP32 serial link and does not
- The storyteller service has been failing at every start since at least 22 July, because of one word in its start command. A builder following this step would get a device whose listening storyteller never starts. The fix is to start `assistant.main` or to add a `__main__.py` to the package
- Nothing tests the installer. It was checked only by being run on this one Pi

## In the maker's words
Asked on 20 November 2026 whether anyone else has built a Moo with the installer, the maker answered that no one has. For now the maker is the only builder, so the fixed user name and the manual Comitup step have not yet stood in anyone's way.
