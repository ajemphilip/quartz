# Goals
- Reach the Raspberry Pi inside the device from the Mac, without a monitor, keyboard or cable
- Find out where the code that the Pi runs actually lives, and whether the copy on the Mac is the same
- Put the Pi code under version control, on the Mac and on GitHub, before it is changed again, so every later change can be undone
- Agree on one way of changing the code that keeps the Mac copy and the Pi copy the same

# Description
After the Bluetooth work of 22 July 2026 (step 30) the Pi code was not touched for four months. Before changing it again, this step checks what is on the device and how to work on it. It is the first step of this workbook written on the day of the work and not reconstructed from files afterwards.

The Pi was switched on and joined the home wifi. From the Mac it answered under its own network name, `moo.local`, and accepted a login over SSH with the key already stored on the Mac. A minute after boot the setup service and the Bluetooth service were running and the storyteller was still starting.

The question was whether a USB cable between the Mac and the Pi would be a better connection. It is not. The Pi Zero 2 W has a single USB data port, and `install.sh` switches it to host mode so that the USB sound card with the microphone and the speaker can plug in. A cable from the Mac into that port gives no network and takes the sound card's place. The settings that once let the Pi appear as a network device over USB during development were removed by the same script. The second USB socket only carries power. Wifi is therefore the working connection, and the setup hotspot or Bluetooth of step 30 remain the way back in if the Pi loses the home network.

The code that the Pi runs is not the copy in the home folder. `install.sh` copies the source into `/opt/moo/pi`, and the three services start from there with the Python environment in `/opt/moo/venv`. Two older copies from the Bluetooth work of 22 July sit beside it. The copy in the home folder is a staging copy that still holds an older build of the setup app. A file by file comparison with checksums showed that the `pi` folder on the Mac is identical to `/opt/moo/pi`, so the Mac copy is a true record of what runs on the device.

That copy had never been committed. The repository on the Mac held the setup app and its GitHub Pages workflow, and the last commit was the Bluetooth diagnostics of 22 July, but the `pi` folder, `build.sh` and `BLUETOOTH_SETUP.md` were untracked. They were committed as one snapshot with a small ignore file for Python's compiled cache. Later the same evening the commit was pushed to the repository on GitHub, `moo-moo-dashboard`, which is public. The Pi code is therefore open to anyone, as the open source aim on the home page asks, and it contains no keys or passwords. The push also rebuilt the hosted setup dashboard through its GitHub Pages workflow, which finished without error and left the app as it was.

## What the check found
The storyteller service was still starting ten minutes after boot. Its log shows why. It starts the Python package `assistant` as a program, but the package has no `__main__.py`, so Python stops at once and the service tries again ten seconds later. The log goes back to 22 July 2026 and every recorded start failed. The listening storyteller has therefore not run as a service since at least that day. Stories started from the phone still work, because they run inside the setup app. The fix is one word in the service file and is left for the next day of work, so that it can be made and tested on its own (step 33).

The same evening the parts of the code that this workbook had not described were written up from the code and from the running Pi. The Bluetooth bridge, factory reset, the wifi manager, the hosted dashboard and the one test went into step 30. How a blank card becomes a Moo became step 33.

## The first change made this way
The maker's trial of the story from the phone led to the first change made with the new workflow, on the same evening.

| | Before | After |
|---|---|---|
| Length of a story part | 2 to 4 sentences, about 60 words, 20 to 30 seconds | 3 or 4 sentences, about 40 words, about 15 seconds |
| The child's turn | In the middle. Each part had one missing word, and Moo stopped at it to ask the child | At the end. Moo tells the whole part, then asks what happens next |
| End of listening | After 1.8 s of quiet | After 3 s of quiet |
| Longest answer | 15 s | 30 s |
| Time to start speaking | 8 s | 12 s |

The missing word was a deliberate design. It put the child's word inside the story, but it also cut the story in the middle of a sentence, which is what the maker heard as unnatural. The phone story already had a second path for a part without a blank. Moo reads the part through, asks what should happen next and weaves the answer into the next part. Telling the model to leave no blank makes that second path the normal one. The listening values matter because the microphone sits inside the casing, where a quiet child who stops to think was taken as finished.

The change was made in the copy on the Mac and committed, the folder on the Pi was saved, the three changed files were copied over, and the setup app was restarted. It answered again within a few seconds, and a comparison showed the Pi and the Mac identical. The maker tried it a few minutes later. Both answers were recorded in full, the first for 11.8 seconds and the second for 8.7, each ending after 3 seconds of quiet.

## The second change, answers and buttons
The trial raised two more points. Moo took any answer, even one that did not fit the question, and some presses on the braille cell seemed to be ignored.

For the answers, Moo now checks what the child said against the question it asked, using the same language model as the story. A silly or imaginative answer counts. An empty answer, filler sounds, an answer cut off in the middle, one about something else or one that is not safe for a child does not. When the answer fits, Moo says it back in one short sentence, so the child knows they were heard. When it does not, Moo asks once more in simpler words, never saying the child was wrong, and uses the second answer as it comes. This applies to the story idea at the start and to every "what happens next".

For the buttons, the code showed two ways a real press could be lost. The driver kept only the last press, so two presses that came between two checks counted as one. And during spelling, presses were cleared after the dots of a new letter had risen, so a press made while Moo was still saying the letter was thrown away. The driver now keeps every press in order, and spelling clears old presses before the letter is announced.

Whether a click reaches the Pi at all is a question for the hardware, so the setup app gained a Button check on the dashboard. The six dots are drawn in the same layout as in calibration (step 31). Each press lights its dot and adds to its count, and the latest presses are listed with how long ago they came. If a dot clicked five times shows fewer, clicks are lost before the Pi. If it shows more, the button bounces. The motors do not move during the check. The three new requests were added to the Bluetooth bridge (step 30), so the check also works over Bluetooth.

On the Pi the check answered at once, with the real hardware and not the dry run, and the new page loaded.

The maker then ran the button check on the device and reported that the buttons now work.

## The third change, a new order and three word games
In the second trial the maker felt the order was wrong. Moo told a part, asked what happens next, ran the spelling game and then asked a separate yes or no question about going on. The maker wanted the story first, then spelling, then the continuation, and asked for ideas. Of the ideas offered, the maker chose having Moo raise a letter and ask the child to name it, and added two of their own. The games should be mixed, and some rounds should be a riddle about the word, with every dot down, so that the child has to press the dots to make the letter.

Each round now has three parts. Moo tells the whole part. Then comes one word game with a word from that part. Then Moo asks what happens next, and the child can say "the end" to finish, which replaces the yes or no question. The word is 3 or 4 letters long for children up to five and 4 to 6 letters after that.

| Game | What the child does | Help Moo gives |
|---|---|---|
| Spell the word | Feels each raised letter and presses its dots down | One gentle word per letter if a lowered dot is pressed, a chime for each cleared letter, and the whole word said at the end |
| Name the letter | Feels one raised letter of the word and says out loud which letter it is | A second try, then Moo names the letter and lets the child feel it once more |
| Riddle and make the letter | Hears a riddle about the word and guesses it out loud. Then, with every dot down, presses the dots of the word's first letter to raise them, and presses a wrong one again to lower it | A note when a dot does not belong to the letter, the letter raised to feel after 45 seconds, and the letter shown after 90 seconds |

The games are mixed at random and the same game never comes twice in a row. Children up to three get spelling and naming only, because building a letter from memory is the hardest of the three. In the building game a press now raises a dot instead of lowering it, so the Pi ignores a press that comes right after a motor starts and a repeat of the same dot within 0.8 seconds. Both can be electrical noise from the motors rather than a finger.

Before it went onto the device, the whole round was run on the Pi in a temporary folder with a pretend cell, a pretend voice and a pretend language model, once for each game. That run found one error, which was fixed before installing. The phone shows each game, the letter being read and, in the building game, the six dots in the layout of calibration, with the dots the letter needs and the dots already raised.

The trial also showed a new kind of problem. The button check had been left open on the phone, so it kept the braille cell and the story could not start. Stories and letter practice now take the cell over from a button check.

The maker then asked for the three games to be available on their own as well. They moved into one shared part of the code that the story and a new Word games screen both use. On that screen, under Play with Moo, the child or parent picks Spell a word, Which letter is this, Riddle and make a letter, or a mix of all three. Without a story to take a word from, Moo picks a simple word of the right length for the child's age, plays the game, and asks whether to play another. "The end", "stop" or two silences end the session. The games are also open over Bluetooth.

The next trials brought seven small corrections, collected while a story was still running and installed together once it had ended, so that no story was cut off by a restart.

| What the maker noticed | Cause | Change |
|---|---|---|
| A spelling word was cut short, "boog" for "booger" | The word picker asked for 3 or 4 letters, and the model shortened the word to fit | The length is only a preference. The word must be whole and appear in the story, or Moo takes a whole noun from the story instead |
| Moo repeated the child's answer back | The answer check of the second change said a fitting answer back | Moo goes straight on. The chime at the end of listening already tells the child they were heard |

## The fourth change, AI without OpenAI
With the games working, the maker asked for a way to run everything without the OpenAI service: the child's speech, the story and Moo's voice worked out on a laptop or a phone, with the user choosing between local and cloud. The maker added that it had to work out of the box from the Moo's website on the home network, on any device.

The Pi itself cannot do it. With 512 MB of memory it has no room for a story model. So the work goes to another device on the same network, in one of two ways.

| Way | What runs where | What it needs |
|---|---|---|
| Moo Local on a computer | A small service on the Mac answers the Moo's requests in the same form as OpenAI. A 3 billion parameter Llama model through Ollama writes, Whisper listens, Piper speaks. It announces itself on the network, so the Moo finds it | A one time install on that computer |
| Lend a device | Any newer phone or computer opens the Lend page of the Moo in its browser. The page loads a Llama model, Whisper and the Kokoro voice into the browser and runs them on the device's own graphics chip. It asks the Moo for work and sends the answers back | A modern browser, the page left open, and about 1 GB on a phone or 2.5 GB on a computer downloaded the first time |

The choice lives on a new AI engine screen, with three options. Cloud is OpenAI with a key. Local is a computer found on the network. The third is a lent device. The setup wizard offers the local way instead of a key, so a family without an OpenAI account can still set the Moo up.

Browsers only allow AI on the graphics chip, and keeping a phone's screen awake, on secure pages. The Moo's page had always been plain http. The Moo now also serves its pages over https on port 8443, with a certificate it makes for itself the first time. Each browser warns about that certificate once. A small check page, opened after the warning, reported a secure page, WebGPU and a working graphics chip on Chrome on the Mac and on an iPhone 16 Pro.

Because the device always calls the Moo and never the other way round, no address on the phone has to be known and nothing has to be installed on it. Inside the Moo the lent device looks like one more AI service, so the story, the games and the checks did not change. Before anyone used it, a stand-in device written as a script answered a story, a safety check, a voice line and a listening job through the queue, each within a few seconds.

The maker's first story ran through Moo Local on the Mac. The maker felt that the local machine could understand the prompts better and could have a better voice. The first choice of models had been the smallest that would work: Llama 3.2 3B for the story, Whisper small for listening and the Piper voice Amy. The Mac, an M5 with 16 GB, has room for more, so all three were replaced.

| Part | First choice | After the maker's trial | Tested from the Pi |
|---|---|---|---|
| Story and checks | Llama 3.2 3B | Gemma 3 12B | About 6 seconds a part, 15 for the first while the model loads. It turned "um the cow" down as unclear, accepted "ess" as the letter S and wrote a riddle for snow |
| Listening | Whisper small | Whisper large-v3-turbo | Heard "Hello, I am Moo. What story would you like today?" exactly, where the small model had heard "L'am-moo" |
| Voice | Piper, Amy | Kokoro, af_heart | The natural voice that the lend page also uses |

The larger model still broke two rules now and then. It greeted the child before the story and ended it with a question. These are now cut from every part in code, whichever model writes it.

Asked whether the voice could be more expressive, eight samples of the same three story lines were made on the Mac. Six were Kokoro voices, warm, bright, soft, British, slower and playful. Two were Chatterbox, a newer model that acts the lines, at two levels of expressiveness. Chatterbox sounded far more alive, but on this Mac it needed 20 to 60 seconds for one short sentence. With the 12 billion parameter story model already loaded, the two did not fit into 16 GB together and the computer kept moving memory to disk. Chatterbox stays as a choice, labelled as very slow, and frees its memory as soon as another voice is used.

The maker asked whether there were other expressive voices, and named Orpheus. Orpheus is a 3 billion parameter voice model that reads small cues written into the text, such as `<giggle>`, `<laugh>`, `<sigh>` and `<gasp>`, and performs them. Four samples were made with the voices Tara, Leah, Mia and Leo. When Orpheus is chosen, the story model is allowed to write up to two of these cues into a part. The Moo removes them from the words shown on the screen, and the other voices drop them before speaking.

| Voice | Sound | Time for about 10 s of speech on this Mac |
|---|---|---|
| Kokoro | Clear and even, ten voices | About 1 s |
| Orpheus | Acted, laughs and sighs | 17 s on its own, 30 to 40 s right after Gemma 12B |
| Chatterbox | Acted, expressiveness can be set | 20 to 60 s per sentence |

Inside Moo Local, Orpheus first failed every time with a timeout of the Mac's graphics processor. It now runs as a separate program that Moo Local starts once and keeps. Even then, the first try right after the 12 billion parameter story model has written a part still times out on a 16 GB Mac, and the second try works. Moo Local therefore tries twice, and if both fail it speaks that line with Kokoro so the story does not stop. With the smaller Llama 3.2 3B story model no try failed. Orpheus is the most alive of the three voices, but a child waits half a minute for each part.

After listening to both on the Moo, the maker judged the expressive voices too slow for what they add. They give the story a different feel, but the fidelity is about the same as Kokoro. The maker asked for many more models instead, down to one that answers almost at once, with the setup reached that evening counted as the second highest tier.

The maker then asked for other voice models to be looked up. Three were installed on the Mac and timed with the same three story lines, with no story model in memory. The maker also found the voice a bit muffled. The Pi now lifts the treble of everything Moo says before it is played, rising from nothing at 1.5 kHz to 6 dB at 4 kHz and above, and turns the sound down if the lift would distort it. For twelve seconds of speech this takes half a second on the Pi. The amount is one number in the configuration, `clarity_db`, and 0 turns it off. The maker listened and found it still a bit muffled. The lift was doubled to 12 dB, a third as much is now taken off the notes below 250 Hz, where a closed case booms, and the AI engine screen gained a Clarity slider from 0 to 18, so the amount can be set by ear with the test line.

Two more voice models were then timed on the Mac with the same three lines. Kitten TTS, the smallest, made 10 to 14 seconds of speech in about one second with its 80 million parameter model and in a quarter of a second with its 15 million parameter one. Qwen3-TTS with 0.6 billion parameters needed 5 to 11 seconds for 13 to 15 seconds of speech, and can be told in words how to read. Samples of both were sent to the maker. Both were then added to Moo Local, Kitten with eight voices and Qwen3 with four, read as a storyteller. The program that ran Orpheus on its own now serves all three.

Measured as the energy between 2 and 8 kHz against the energy between 200 Hz and 2 kHz, the 47 voices differ by 19 dB. The noise was traced to the way the Pi changed the sample rate, by straight lines between samples, which adds a hiss above the voice that the lift then made louder. The rate is now changed through the spectrum of the sound, and the hiss measured 88 dB below the voice. Commit `78278b8`.

# How it works
## Where the code lives
| Place | What it is |
|---|---|
| `RaspberryAndPython/pi` on the Mac | The copy that is edited. Now under git |
| `RaspberryAndPython/app` on the Mac | The setup app. `build.sh` builds it into `pi/setup_service/static` |
| `/opt/moo/pi` on the Pi | The copy the services run, put there by `install.sh` |
| `/opt/moo/venv` on the Pi | The Python environment of the services |
| `pi` in the home folder of the Pi | An older staging copy, not used by the services |

## Changing the code
1. Edit the file on the Mac and commit it
2. If the setup app changed, run `build.sh` first
3. Copy only the changed files to `/opt/moo/pi` over SSH, after saving a copy of the folder on the Pi
4. Restart the one service the change belongs to. `moo-assistant` for the storyteller, the braille cell and audio, `moo-setup` for the setup app, `moo-bluetooth` for Bluetooth
5. Read the service log, then test on the device. If something breaks, put the saved copy back

# Critical Reflection
## Wifi and a copy on the Mac
**Pros**
- No monitor, keyboard or cable. The device stays closed and can sit where it is used while its code is changed
- The Mac copy and the device copy were proved to be the same before anything was edited, so the starting point is known
- Every change from now on is a commit, and every copy to the Pi is preceded by a saved copy on the Pi, so a change can be undone on either side
- The workflow needs nothing that a builder of another device would not have. A computer on the same wifi and an SSH login to the Pi

**Cons**
- The connection depends on the home wifi. On a network that blocks the `.local` names, or away from home, the Pi has to be found another way
- The single USB data port cannot serve both the sound card and a development cable, so there is no wired fallback while the device is assembled
- Two copies can drift apart again if a file is ever edited directly on the Pi. Only the Mac copy is under git
- The code and the setup dashboard share one repository, so every push of Pi code also rebuilds the dashboard
